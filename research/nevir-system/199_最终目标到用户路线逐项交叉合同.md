## 这份合同解决什么

最终标准不能只写成“简单、清晰、全面、能迁移、达到NL50”。这些词必须落到用户实际走过的路线和页面交接上，否则后续增加文档或题目时，无法判断是否真的补上了目标要求。

199号把目标矩阵的 G1—G10 逐项连接到：

```text
用户路线：L0 → L1 → L2 → L3 → L4 → p1 → p2 → p3 → p4 → p5 → p6 → p7
作者阶段：C0 → C1 → C2 → C3 → C4 → C5 → C6 → C7 → C8 → C9
```

每项要求都必须有四种记录：

1. 用户会经过哪些路线状态；
2. 作者侧哪些阶段必须先完成；
3. 页面或状态机要交接哪些字段；
4. 当前真实状态和阻断闸门是什么。

交叉表还为每个证明字段登记唯一来源。例如，`currentState`、`nextState`、`requiredInputs`、`requiredOutput` 和 `errorReturn` 必须来自首遍状态交叉表；`rangeBefore`、`physicalFilter`、`actionFilter`、`rangeAfter` 和固定分母必须来自视觉编译合同；`successorOrStop`、`rangeConservation` 和 `ledgerConservation` 必须来自慢速执行与连续账本合同。字段没有来源时，机器审计会失败，不能只因为目标行已经写出来就算闭合。

这次反向检查还要求每个状态的 `requiredOutput` 必须被下一状态接收、被当前记忆/独立证据消费，或明确标记为终点输出。由此补上了四类容易被遗漏的交接：位置从 p1 传入 p2，物理组合和原始分母从 p3 传入 p4，课程动作候选从 p4 传入 p5，回应或新牌从 p6 传入 p7；p7 的 `stopOrSuccessor` 只在路线终点保留。这样“页面上显示过”不能代替“下一步真正收到”。

## 不允许从交叉表推出的结论

这张表只证明“目标要求已经有路线位置、作者阶段和证据入口”。它不能推出：

- 页面已经按路线运行；
- 参考策略已经和课程输入完全匹配；
- 35项已经具备精确答案；
- 学习者已经能在陌生题上执行；
- 学习者已经达到NL50或能稳定盈利。

缺少运行时、匹配参考或学习者证据时，交叉表必须保持纸面状态，不能把映射数量转换成完成百分比。

机器交叉表见 [goal-route-requirement-crosswalk.json](goal-route-requirement-crosswalk.json)，其中 `proofFieldRegistry`、`proofFieldCoverage` 和 `routeOutputConsumption` 保存了字段来源及逐状态消费结果。
