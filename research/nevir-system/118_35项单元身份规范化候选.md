## 这次补的不是策略，而是“这项练习究竟属于哪里”

原来的35项字段审计已经发现：每个单元都有编号、父层、来源和题目，但街次、角色、行动状态、范围、后继和发布状态没有统一字段。这样即使题目本身有内容，页面也不能可靠地知道它应挂在翻牌、转牌还是河牌，也不能知道它是“面对下注”还是“回应更新”。

这份候选层只从已有 `sourceScopedIdentity`、`gameFrameCandidate`、`knownIdentity` 以及单元明确指向的来源 JSON 抽取身份，不补写任何策略。来源 JSON 的补充字段都保留了 `sourceFallback.fields[].reason`，可以逐项追溯：

- 父层：35/35；
- 行动状态：35/35；
- 街次：34/35；
- 角色证据：24/35；
- 位置对：31/35（英雄位）、30/35（对手位）；
- 牌面：33/35；历史：32/35；底池：31/35；双方剩余筹码：26/35；
- 额外可追溯字段：英雄底牌20/35；单一活动筹码5/35。

这里的“双方剩余筹码”只在来源明确给出英雄/对手的筹码时才登记；`size-comparison` 里只有一个 `activeStackBB`，所以单独保存，不能把它复制成双方筹码。多案例包（例如 `first-pass-structure-packet`）没有把案例和某个单元一一绑定，因此仍不回填。

因此它能让系统先完成可靠的路线挂接，例如把已有单元标成“河牌、无下注、翻前最后加注者”，但不能让系统凭空生成“应该下注”“对手范围是什么”或“下一张转牌怎么继续”。

## 用户体验上的作用

用户不会看到“35项字段审计”。当他从翻后父层打开一个单元时，系统至少可以先告诉他：

1. 这是哪一街；
2. 当前属于无人下注、面对下注、面对加注、回应更新还是新牌更新；
3. 这项内容属于哪个父步骤；
4. 当前缺少什么输入，为什么还不能进入精确动作题。

如果街次或角色没有来源，页面必须显示“当前资料没有确认这一项”，并停在事实/示范层；不能根据相邻单元、同一牌面或标题推断。这样学习者会知道自己停在哪里，作者也不会把单元编号误当成课程完成。

## 缺口优先顺序

当前仍缺完整身份的单元主要是 `1.1、1.3、1.5、1.7、1.8、3.6、4.3、4.5、4.6、5.1—5.8`。其中 `1.x` 只有单一活动筹码，`3.6` 是未绑定到具体案例的多案例包，`4.x/5.x` 仍有角色、对手位或金额缺口，因此不能直接开放连续练习；还要先知道前一行动或新牌到底发生在什么街次、由谁执行、范围从哪个父快照继承。

补齐身份后还要按顺序补：课程规则 → 匹配参考 → 动作前后范围 → 合法后继 → 单变量迁移。身份候选本身不提高35项的策略发布等级，也不改变资料不足时的停止规则。
